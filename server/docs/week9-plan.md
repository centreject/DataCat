## 9-A. PR #9 리뷰 반영과 대기 시간 기준 정리

1. PR 댓글 2건을 검토하고, 마이크 개방 전 안내 재생을 필수 규칙으로 명세에 유지한다.
2. 음성 읽기 기본값은 5초 유지. `MODEL_AUDIO_READ_TIMEOUT_MS`로 양수 밀리초 값을 받도록 분리한다.
3. 기본 5초에서 지연 응답이 503으로 처리되는지, 10초 설정에서 8.5초 지연 응답을 받는지 자동 검증한다. 이는 지연 HTTP 시험이며 실제 추론 시간 시험이 아니다.
4. 현재 변경과 결과를 PR #9에 추가하고 팀 리뷰 기준에 맞춰 병합한다. 이 문서는 푸시·병합 완료 증거가 아니다.
5. MODEL_BUSY 세분화와 전체 synchronized 제거는 이번 기본 시연 범위에 즉시 도입하지 않는다. 다중 기기를 정식 지원할 때 상태 경쟁·재시도 정책과 함께 설계한다.

### 세 종류의 시간을 분리한다

| 구간 | 현재 기준 | 확인 방법 |
|---|---|---|
| Spring → 모델 접속 | 2초 | 연결 실패 사례와 실제 연결 환경 확인 |
| Spring → 모델 읽기 | 사진 5초, 음성 기본 5초. 음성은 환경변수로 변경 가능 | 모델 단독 처리·대기 시간과 지연 HTTP 시험 |
| Pi → Spring | Pi 브랜치 api_client.py의 TIMEOUT_S는 10초 | 사진·음성 업로드, 서버 잠금 대기, 모델 처리, 응답 시간을 포함해 실측 |

읽기 타임아웃은 전체 요청의 벽시계 시간 상한과 같지 않다. Spring 읽기를 10초로 올릴 때 Pi도 10초로 두면 전송·대기 여유가 없을 수 있다. Pi 값을 별도 검토하며 15초 이상 등의 후보는 측정 후 팀과 확정한다.

## 9-B. Docker 실행을 다른 PC에서도 재현

앱 담당 브랜치 `feature/app-design`에 `datacat-stack/docker-compose.yml`과 `docker-compose.spring.yml`이 이미 있다. 기존 구성을 최신 server/model-service와 결합한다. 앱 브랜치의 이력 문제는 해당 담당과 조율하고 저장소 전체를 강제로 병합하지 않는다.

| 작업 | 인태 담당 확인 | 완료 증거 |
|---|---|---|
| 실행 경로 | Compose의 SPRING_DIR·MODEL_DIR 및 Java 21 빌드 | 같은 커밋과 명령으로 Spring 시작 |
| 모델 주소 | 컨테이너 안에서는 http://model:8000 등 실제 서비스명 | 사진·음성 요청 성공. localhost를 다른 컨테이너로 오해하지 않음 |
| DB | Compose의 db:3306, 개발 PC 외부 접속 포트 구분 | MySQL에서 동일 방문 조회 |
| 영속성 | DB와 SNAPSHOT_DIR Volume | 재기동 후 방문·사진·토큰 유지. 시험 중 volume 삭제 명령 사용하지 않음 |
| 푸시 | 기존 Compose에 자격 증명 경로가 있어도 Spring의 FCM_ENABLED를 따로 활성화 | Android 실제 푸시 수신, 앱 데모 모드 해제 |
| 음성 대기 | Compose 환경변수에도 MODEL_AUDIO_READ_TIMEOUT_MS 전달 | 실제 실행 값과 기록 값 일치 |
| 공유 | 비밀 값 없는 설정 예시와 시작·종료 README | 다른 팀원 PC에서 재현 또는 함께 화면 확인 |

이 단계의 완료 기준은 Docker 파일을 작성했다는 것이 아니라 실행·재기동·데이터 유지 확인이다. 현재 배포 키·실제 사진·음성·DB Volume을 제출 압축에 포함하지 않는다.

## 9-C. 실제 Pi·모델·앱 통합

인태는 Spring 실행·API 응답·DB·푸시·시간 기록을 맡고, 수연은 센서·카메라·마이크·스피커 동작을 맡는다. 민중은 실제 모델 환경·입력별 추론 결과, 덕민은 앱 표시·알림·프리셋 문구 일치를 함께 확인한다.

| 번호 | 시험 | 통과 기준 |
|---|---|---|
| P1 | 사진 → 안내 → 실제 택배 발화 → 음성 업로드 | 동일 eventId, 접수 안내가 끝난 뒤 녹음, /audio 200, 배송 결과 저장, 완료 음원 1회 재생 |
| P2 | 방문객이 안내 전에 이탈 | Pi 재확인 후 /end VISITOR_LEFT, END_SESSION. 불필요한 녹음 없음 |
| P3 | 발화 없이 대기 종료 | /end TIMEOUT 또는 합의된 무발화 흐름, 오류 없이 초기 감시 복귀 |
| P4 | 모델 장애·네트워크 단절 | HTTP/연결 오류 구분, 마이크 닫기·임시 파일 정리·오류 안내 1회. 현재 상태별 재시도 계약 준수 |
| P5 | 같은 성공 녹음 재전송·늦은 종료 | 재분석·추가 푸시·기존 결과 덮어쓰기 없음 |
| P6 | 사진 알림 → 음성 결과 알림 → 상세 | 동일 방문 알림 갱신, 중복 누적 없음, 상세 사진·전사문·분류·요약 일치 |
| P7 | 물품 유지 → 미감지 1회 → 2회 → 새 도착 | 유지 중 반복 알림 방지, 1회 미감지에서 유지, 2회에서 해제, 재도착 시 새 기록 |
| P8 | 장치·서버 재시작 | 감시 복귀, DB·사진 유지, 앱 목록·상세 조회 가능 |

우선 P1~P4를 실제 장치로 각 3회 반복하고 P5~P8은 최소 1회 확인한다는 작업 제안이다. 시험 횟수는 팀 일정에 맞춰 조정할 수 있으나 성공 한 번만으로 모든 경우를 완료 처리하지 않는다.

### 음원 매핑

- presetId 1: 인사·녹음 안내. 최종 녹음 사실 안내 문구와 Pi 실제 파일 확인.
- presetId 2: 접수 완료. 서버 text와 투표로 확정한 실제 음원 문구 일치 확인.
- 오류 안내: 네트워크/503 실패 때 Pi가 보관한 오류 음원 1회 재생. 실패 응답에 성공 프리셋 2가 온다고 가정하지 않는다.
- END_SESSION과 SILENT_STANDBY의 재생 여부를 구현 계약과 맞춘다. 모든 응답에 음원을 재생하는 식으로 처리하지 않는다.
