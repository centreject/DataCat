# 음성 접수 구현 및 통합 확인 사항

## 현재 연결한 계약

- Pi: `POST /api/v1/device/events/{eventId}/audio`, multipart `audio`.
- Spring: 모델의 `POST /internal/v1/audio/process` 호출 후 판정표 C 적용.
- 성공: HTTP 200, `COMPLETED`, `PLAY_PRESET`, 프리셋 2 `접수되었습니다.`.
- 전사문·용건·배송 세부 유형·요약·앱 표시 정보는 같은 Event에 저장한다.
- 방문 저장과 잔류 물품 상태 저장을 하나의 트랜잭션으로 처리한다.
- 모델 호출은 DB 트랜잭션 밖에서 실행한다. 커밋 후 비동기 푸시를 요청한다.
- 사진 단계의 처리 상태와 확인 필요 여부를 별도 컬럼으로 보관해 음성 재분석에서도 유지한다.
- 원본 음성은 DB나 별도 영구 파일에 저장하지 않는다. Spring multipart 임시 파일은 요청 종료 시 프레임워크가 정리한다.

## 재전송·추가 음성 처리 — 구현 제안

이 절의 재전송 및 유예 세부 기준은 API 명세 6.3에 구현 제안으로 기록했다. 통합 시험과 담당자 확인 후 확정한다.

| 요청 시점·상태 | 현재 처리 |
|---|---|
| WAITING_AUDIO | 첫 음성을 접수한다. 사진 후 30초를 넘겼다는 이유만으로 첫 음성을 거절하지 않는다 |
| 음성으로 완료된 방문에 마지막 성공 녹음과 같은 파일 재전송 | SHA-256으로 비교해 HTTP 200과 기존 완료 응답을 반환한다. 모델·DB 갱신·푸시를 다시 실행하지 않는다 |
| 음성으로 완료된 방문에 다른 녹음 전달 | 마지막 성공 사진의 서버 처리 시작 시각부터 30초 이내일 때 재분석한다. 기존 사진 병합 기준에 맞춘 시작값이다 |
| /end·사진 판정·분석 동시 실패로 완료된 방문, FAILED | HTTP 409. 새 방문으로 접수한다 |
| 모델·DB 처리 실패 | 성공 녹음 해시를 갱신하지 않는다. 정상 사진의 음성 503은 대기를 유지하고, A0의 음성 503은 별도 오류 종료 규칙을 따른다 |

`audioHash`는 마지막 성공 녹음의 식별용 요약값이다. 파일 이름은 비교에 사용하지 않는다.
다른 녹음으로 갱신한 뒤 과거 녹음이 늦게 다시 오면 새 녹음과 구분할 수 없다.
재전송 식별자 또는 녹음 순번의 도입 여부와 추가 음성 유예 시간의 정확한 기준은 **TBD**다.
무음 모델 결과는 정상 응답으로 저장하며 판정표 C의 `무응답` 처리를 적용한다.

## 오류와 현재 한계

- 잘못된 번호·누락·빈 파일·16MB 초과: 400.
- 없는 방문: 404. 현재 상태에서 접수 불가: 409.
- 모델 연결·응답 오류: 503. DB·파일 읽기 오류: 500.
- 사진·음성·종료 처리는 같은 `DeviceEventService`의 `synchronized` 잠금을 사용한다.
  한 Spring 프로세스에서 순차 처리하며, 모델 처리 중 다른 장치 요청도 기다릴 수 있다.
  여러 Spring 인스턴스 사이의 동시성은 제어하지 않는다.
- 사진 접수의 A-1 연결과 10-23 물품 존재 정책은 추가 구현했다. 상세한 규칙·DB 호환·검증 범위는 `package-state-integration.md`를 따른다.
- 실제 Pi·실제 모델 시험과 타임아웃 실측은 통합 단계에서 확인한다.
- 수정 APK에서 배송 알림 수신과 22번 방문의 상세·사진·전사문·요약 표시를 확인했다.
- A0와 음성 503의 오류 종료를 추가했다. 정상 사진의 음성 장애는 대기를 유지한다.
  상세 동작과 팀 확인 대상인 세부 값은 `model-failure-handling.md`를 따른다.
