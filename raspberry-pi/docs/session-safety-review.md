# Pi 응대 오류 처리 검토안

2026-11-26 · 기준 main `975a505` · 검토 대상: 수연(Pi), 인태(서버 연계)

## 변경 이유와 범위

기존 코드에서 안내음 재생이 실패해도 `record_utterance()`가 호출되는 문제를 재현했다.
또 마이크 `OSError`는 바깥 감시 루프로 전파돼 서버에 장치 오류 종료를 알리지 않았다.
명세 v1.6.1의 5.3·6.3·6.4와 [PR #21 리뷰](https://github.com/centreject/DataCat/pull/21#issuecomment-7092704119)를 기준으로 응대 흐름을 보완한다.
서버의 `DEVICE_CANCELLED` 처리·자동 만료는 PR #11에서 이미 구현됐다.

| 상황 | 수정안의 동작 |
|---|---|
| 녹음 안내 멘트 재생 성공 | 재생 함수가 끝난 뒤 마이크 개방 |
| 녹음 안내 멘트 재생 실패 | 오류 표시용 삐 소리를 시도하고, 삐 소리 성공 여부와 무관하게 녹음 차단·`DEVICE_CANCELLED` 전송 |
| 마이크 열기/녹음 중 `OSError` | `TIMEOUT`과 구분해 `DEVICE_CANCELLED` 전송 |
| 정상적인 발화 없음 | 기존 `TIMEOUT` 유지 |
| 안내 전 방문객 이탈 | 기존 `VISITOR_LEFT` 유지 |
| `/audio` HTTP 409 | 같은 녹음을 재전송하거나 완료 안내를 재생하지 않고 현재 응대 정리. 바깥 감시 루프는 기존처럼 `CLEAR`를 기다림 |
| `/audio` 503·연결 오류 | 기존 오류 안내 유지 |
| 종료 전송도 실패 | 로그를 남기고 녹음 차단 유지. 서버의 대기 방문 자동 만료(기본 120초)가 정리 |
| 분석 완료 후 완료 안내만 실패 | 이미 저장된 성공 결과를 장치 오류 종료로 덮어쓰지 않음 |

PR #21 리뷰는 안내음·삐 소리가 모두 실패하는 상황을 지적했다.
이번 안은 명세 5.3의 녹음 사실 안내 요구에 따라, 삐 소리가 성공해도 녹음 안내 멘트 실패를 성공으로 간주하지 않는다.
수연님이 실제 운용 흐름을 검토할 때 이 기준도 함께 확인한다.

## 장비 없는 검증 결과

작성 환경: Linux · Python 3.12.14 · 2026-11-26.

- 수정 전 코드에 새 시험을 적용해 안내 실패 후 녹음 호출, 마이크 오류 전파, 409 오류 안내 재생을 검출했다.
- 수정 후 `cd raspberry-pi && python -m unittest -v`: **51개 통과**(기존 38 + 추가 13).
- 추가 13개 중 2개는 로컬 `ThreadingHTTPServer`와 `SpringClient`로 HTTP를 실제 송수신한다.
  - 안내 실패: `/api/v1/device/events` 다음 `/api/v1/device/events/41/end`에 `reason=DEVICE_CANCELLED`, `/audio` 없음.
  - 409: `/audio` 한 번만 전송, 추가 `/audio`·`/end`·완료 안내 없음.
- 상대 HTTP 서버는 시험용이다. 실제 Spring의 DB 저장, Android 화면, 실제 음원·센서 동작을 입증하지 않는다.
- Windows·Docker·실제 Pi에서의 이번 수정안 시험은 적용 후 별도로 기록한다.

## 수연님 검토·실장비 확인

먼저 실행 중인 Pi 프로그램을 종료하고 수정안을 별도 검토 브랜치에서 확인한다.
아래 환경변수는 명령 한 번에만 적용되므로 이후 정상 실행에는 남지 않는다.
서버 주소는 실제 Spring 주소로 바꾼다(Docker 서버의 외부 포트는 18080).

### 1. 정상 방문

```bash
cd <DataCat 경로>/raspberry-pi
.venv/bin/python main.py --server http://<서버IP>:18080
```

방문객 접근 후 안내 멘트를 직접 듣고, 안내가 끝난 뒤 마이크 개방 로그가 나오는지 확인한다.
발화 후 같은 방문 번호의 배송 결과·완료 안내·서버 상세를 대조한다.

### 2. 재생 장치 오류 재현

```bash
DATACAT_AUDIO_OUT=plughw:CARD=DoesNotExist,DEV=0 .venv/bin/python main.py --server http://<서버IP>:18080
```

존재하지 않는 출력 장치를 이 프로세스에만 지정한다. 실제 스피커 선을 뽑을 필요는 없다.
접근 후 `녹음 안내 실패 → 마이크를 열지 않고 장치 오류 종료` 로그가 나오고,
`마이크 개방, 발화 대기`·녹음·`/audio` 전송이 없는지 확인한다.
서버에서 해당 방문이 `COMPLETED`, `processingStatus=단말 확인 필요`, `needsReview=true`로 저장되는지 확인한다.

### 3. 마이크 장치 오류 재현

```bash
DATACAT_AUDIO_IN=plughw:CARD=DoesNotExist,DEV=0 .venv/bin/python main.py --server http://<서버IP>:18080
```

정상 안내를 듣고 난 뒤 마이크 오류가 발생하며, 같은 방문에 `DEVICE_CANCELLED`가 보내지는지 확인한다.
정상적인 무발화 `TIMEOUT`과 구분돼야 한다.

### 기록 표

| 항목 | 방문 번호 | Pi 로그 | 서버 상세 | 앱·알림 | 결과 |
|---|---|---|---|---|---|
| 정상 안내 → 녹음 → 완료 | 미기록 | 미확인 | 미확인 | 미확인 | 미실시 |
| 출력 장치 오류 → 녹음 차단 | 미기록 | 미확인 | 미확인 | 미확인 | 미실시 |
| 마이크 오류 → 장치 오류 종료 | 미기록 | 미확인 | 미확인 | 미확인 | 미실시 |
| 정상 무발화 → TIMEOUT | 미기록 | 미확인 | 미확인 | 미확인 | 미실시 |

시나리오를 바꿀 때는 방문객이 떠나 `CLEAR`가 나오는지 확인하고, 사진 요청의 30초 병합 구간도 피한다.
서버가 같은 방문을 재사용하면 새 방문인지부터 확인한다. 사진·녹음 원본이나 Firebase 키를 PR에 올리지 않는다.

## 후속 확인 항목

- 프로그램이 재생 성공으로 반환해도 스피커 전원·볼륨·물리적 고장으로 소리가 안 날 수 있다. 실제 안내 청취는 별도로 확인한다.
- HTTP 409의 로컬 분기는 모의 서버로 검증했다. 실제 Spring 만료·409·자동 만료는 서버 검증 기록과 함께 대조한다.
- 앱의 `단말 확인 필요` 태그와 설명·타임라인은 따로 확인한다. [PR #25 회의 안건](https://github.com/centreject/DataCat/pull/25)에서 오류 방문을 무발화로 설명하는 문제를 지적했으므로, 원본 API 결과와 앱 표시를 구분해서 기록한다.
- VL53L5CX 가림·프레임 타이밍, Docker 오디오 장치 검색, LCD 연결, 녹음 프로세스의 블로킹 읽기·파이프 수명 관리는 이번 패치의 검증 범위에 포함하지 않는다. 수연님이 PR #25의 항목과 함께 우선순위를 정한다.
