# 평가 (정확도)

모두 `model-service/`에서 실행한다. 데이터는 `data/`(git 제외)에 만들어진다.

| 준비 | 명령 |
|---|---|
| 공개 이미지 받기 | `python eval/prepare_images.py` |
| TTS 평가 음성 만들기 | `python -m eval.make_tts_audio` |

| 평가 | 명령 |
|---|---|
| 용건 분류 (규칙만) | `python -m eval.eval_language --rules-only` |
| 용건 분류 (LLM) | `python -m eval.eval_language` |
| 용건 분류 시험셋 (마일스톤에서만) | `python -m eval.eval_language --cases heldout` |
| STT | `python -m eval.eval_stt` |
| 이미지 인식 | `python -m eval.eval_vision` |

프로필은 환경변수 `MODEL_PROFILE=lite|full`로 고른다. 목표치는 [`metrics.py`](metrics.py)의 `TARGETS`(계획 문서의 잠정 목표, full 기준).

## 데이터

- **용건 개발셋** [`purpose_cases.jsonl`](purpose_cases.jsonl): 100건, 용건 9개(반례 포함: "택배 아니고요, 관리실에서…", "정수기 렌탈 홍보" vs "정수기 필터 교체"). 프롬프트·규칙은 이 세트를 보고 고친다 — 그래서 여기 수치는 낙관적이다.
- **용건 시험셋** [`heldout_cases.jsonl`](heldout_cases.jsonl): 64건. 덕민님 기획서(`상황분류_종류와_조건.md`)의 "포함 상황" 표현으로 만든 문장 + 앱 목업 API의 실제 발화 7개(`source` 필드에 출처). **마일스톤에서만 재고, 틀린 문장을 보고 고치지 않는다.** 덕민님이 직접 쓴 문장이 오면 기획서 기반 문장을 그것으로 바꾼다. 개발셋·LLM 예시와 겹치지 않는지 테스트로 확인한다.
- **STT 음성**: 위 40문장을 edge-tts(남·여 음성 번갈아)로 합성. `tts/` 원본, `tts_snr20/`·`tts_snr10/` 백색 잡음 추가. 실제 INMP441 녹음은 `data/audio/real/<id>.wav` + `<id>.txt`로 넣으면 같이 평가된다.
- **이미지**: Open Images 검증·테스트 세트 일부. 배달 음식·보냉백은 공개 데이터가 없어 팀 사진이 필요하다.

### 2026-09-27 · lite 프로필 · RTX 3060 Ti 8GB

**STT** — `large-v3-turbo`, `int8_float16`

| 음성 | 파일 수 | 평균 CER | 목표 ≤ 15% |
|---|---:|---:|---|
| TTS 원본 | 40 | 3.8% | PASS |

가장 많이 틀린 문장: "로켓프레시 보냉백" → "로켓프렛이 본행백" (CER 25–31%). TTS는 실제 마이크 녹음보다 쉬운 조건이므로 실제 녹음으로 다시 잰다.

도메인 단어 보강 후(M6, 같은 날): 원본 3.6%, 잡음 20dB 4.1%, 잡음 10dB 4.7% — 세 조건 모두 개선. "보냉백" 인식됨. 전사 끝에 깨진 글자(U+FFFD)가 붙는 경우를 발견해 필터에서 제거함.

**용건 분류 — 규칙만(LLM 실패 시 대체용)**: 정확도 52% (목표 90% FAIL), 요약 20자 초과 0%. 키워드에 없는 표현(쿠팡, 등기, 치킨, 보일러, 할머니 등)은 대부분 ETC로 분류된다. LLM이 필요한 이유이며, 규칙 보강은 평가셋과 겹치지 않는 문장으로 따로 한다.

키워드 보강 후(M5, 같은 날): **88%** (DELIVERY 재현율 100%, INSPECTION 90%, VISIT 60%). 단, 추가한 단어 상당수(쿠팡, 등기, 보일러, 할머니 등)가 평가셋에도 나오므로 실제보다 좋게 나온 수치다. 보강 단어는 평가셋에 없는 문장(tests/test_language.py)으로 검증했다. 남은 오답: 부정 표현("택배 아니고요"), 가족 호칭 없는 지인 방문.

**용건 분류 — LLM** — `Qwen/Qwen3-4B-Instruct-2507`, 4bit(lite)

| 프롬프트 | 정확도 | 요약 20자 초과 | 파싱 실패 |
|---|---:|---:|---:|
| 첫 버전 | 88% (FAIL) | 0% | 0건 |
| 용건 정의 보강 후 | **98%** (PASS) | 0% | 0건 |

첫 버전은 "방문", "왔다"라는 말만 보고 모르는 사람(교회, 전단지, 호수 확인)을 VISIT으로 분류했다. 프롬프트에 "아는 사이일 때만 VISIT, 영업·종교·설문·길 묻기·전단지는 ETC" 같은 일반 규칙을 넣었다(평가 문장은 넣지 않음). 평가셋에 없는 문장 4개(tests/test_qwen_gpu.py)도 모두 맞혔다. 단, 평가셋 오답을 보고 고쳤으므로 98%는 낙관적이다 — 덕민님 기획 확정 후 100건으로 늘려 다시 잰다. 남은 오답: "인터넷 기사 방문 예약" → ETC.

요약 검증 추가 후(R2 리뷰 반영): 정확도 98% 유지. LLM 요약에 방문객이 말한 단어가 하나도 없으면 전사문을 요약으로 대신 쓴다 — 40건 중 7건 해당(예: "안녕하세요." → LLM "방문 인사" → "안녕하세요."). "가족 방문"처럼 괜찮은 추상화도 함께 걸러지는 대가가 있다(덕민님 요약 문체 확인 때 함께 논의). 요약의 한자(예: "방문者")는 제거한다.

### 2026-10-04 · 요약 명사형 복원 + 시험셋 첫 측정 (마일스톤)

요약 문체를 명사형 쪽으로 되돌렸다(계획 검토 결정): 프롬프트에 "끝을 명사로 바꾼다(두고 갈게요→보관, 왔습니다→도착…)"를 넣고, 요약 검증에서 **마지막 낱말(서술어)만** 활용형 차이를 허용했다(둠←둘게요, 주기←줘, 간다←갈게요). 장소·물건 낱말은 지금처럼 말한 그대로여야 한다. 새 지표 "요약 명사형" = 빈 요약을 뺀 요약 중 "~요/~다/~니다" 같은 문장 끝으로 끝나지 않는 비율.

| 평가 | 용건 | 긴급·위협 재현율 | 배송 세부 유형 | 요약 명사형 | 전사문으로 대체 |
|---|---:|---:|---:|---:|---:|
| 개발셋, 바꾸기 전 | 98% | 100% | 83% | 81% | 15건 |
| **개발셋, 바꾼 뒤** | **98%** | **100%** | **83%** | **86%** | **10건** |
| 개발셋, 음성(잡음 10dB) → STT → LLM | 98% | 100% | 83% | 87% | 10건 |
| **시험셋 64건 (LLM)** | **98%** | **90% FAIL** | **86%** | **89%** | **9건** |
| 시험셋 64건 (키워드 규칙만) | 81% | 80% | 100% | 67% | — |

- 명사형 목표 90%에는 조금 못 미친다. "~다/~요로 끝내지 말라"는 줄을 더 넣으면 91%가 되지만 배송 세부 유형이 78%(목표 80% 미만)로 떨어져서 넣지 않았다 — 세부 유형은 Spring이 쓰는 값이고 문체는 보기 좋은 정도의 차이다. 남은 문장형 요약은 대부분 말하지 않은 장소를 붙여서 전사문으로 대체된 경우다(예: "소포 하나 왔습니다." → LLM "소포 문 앞 보관" → 거부).
- **시험셋에서 위협 1건을 놓침**: "너 거기 있는 거 다 알아, 가만 안 둬." → 불명. 위협 4건 중 3건만 맞아 긴급·위협 재현율 90%. 개발셋(100%)보다 낮은 이 수치가 실제에 가깝다. 규칙대로 이 문장에 맞춰 고치지 않았다 — 보강은 덕민님 시험 문장이 오면 기획서 기반 문장을 개발셋으로 옮긴 뒤 한다.
- 시험셋의 다른 오답 2건은 세부 유형: "커피랑 도시락 배달" → 장보기(정답 음식), "쿠팡… 물건" → 퀵(정답 택배, 개발셋에도 같은 오답).
- 단위 테스트 210개, GPU 테스트 35개 통과(음식·보냉백 사진이 없어 2개 건너뜀).

### 2026-10-17 · 물품 개수를 셀 수 있는가 (판정표 "같은 택배 알림 반복" 대비)

택배 상자·비닐봉투 사진 55장에서 모델의 `package` 개수를 Open Images 정답 상자 수(화면의 1% 이상, 묶음 표시 9장 제외)와 비교하고, 카메라에서 흔한 작은 변화(밝기 ±15%, JPEG 압축, 3% 이동, 80% 축소)를 준 뒤 개수가 바뀌는지 봤다. 스크립트는 로컬(`.superpowers/count_check.py`).

- **개수 정확도 48%**(22/46). 더 세는 경우(봉투·상자·용기 프롬프트가 한 장면의 여러 물건을 따로 셈)와 덜 세는 경우가 섞여 있고, 여러 개가 있는 사진 7장은 1장만 맞았다.

### 2026-10-17 · 돌려 말한 위협 보강 (H7)

시험셋에서 놓친 위협("너 거기 있는 거 다 알아, 가만 안 둬.")은 보지 않고, 시험셋과 겹치지 않는 돌려 말한 위협 8문장과 비슷하지만 위협이 아닌 3문장(관리실 누수 확인, 지인의 "밤길 조심할게", 등기 서명)을 새로 써서 개발셋에 넣었다(100 → 111문장). 덕민님 시험 문장(C10)을 기다리지 않고 진행.

- 바꾸기 전 새 위협 8문장 중 4문장을 놓쳤다("얼굴 기억해 뒀다", "밤길 조심해라", "가족들 다 잘 있지?…", "집에 있는 거 알고 왔어…" → 지인·불명·영업). 원인은 위협 설명의 "**명확히** 언급함".
- 바꾼 것: 위협 설명을 "폭력 낱말이 없어도 해코지·보복을 암시하면 협박이다(두고 보자, 밤길 조심해라, 얼굴 기억했다, 가족 안부로 겁주기)"로 넓힘. 규칙·예시는 늘리지 않음.

판단 규칙 10개와 예시 11개를 하나씩 빼고 개발셋 100문장을 다시 돌렸다(탐욕 디코딩이라 한 번씩이면 결과가 같다). 빼도 지표가 그대로이거나 나아진 규칙 5개를 함께 빼서 다시 재고, GPU 테스트로 확인했다.

### 2026-10-17 · 물품 인식 파인튜닝 1단계 (Open Images, F1) — 서비스 적용

- 데이터: Open Images **train 분할**만 학습에 사용. 상자 1,600 · 비닐봉지 435 · 봉투 116 · 음성(가방·여행가방·문, 물품 없음) 800 = 2,949장(그중 10%는 학습 중 검증용). 그림 속 물품(IsDepiction)·묶음 상자(IsGroupOf)는 뺐다.
- 평가: 학습에 안 쓴 validation 분할 222장 + 기존 평가 사진(`data/images`). 기존 사진과 겹치는 것은 뺐다.
- 모델: YOLOE-11s에서 시작, 클래스 3개(box, envelope, plastic bag). RTX 3060 Ti에서 linear probe 20 epoch 4분, 전체 학습 30 epoch 11분. 전체 학습은 5 epoch 근처가 최고(mAP50 0.62)이고 이후 과적합이라 best.pt를 썼다.

사진 한 장에서 물품을 하나라도 찾은 비율(오탐 줄은 낮을수록 좋음), conf 0.4:

| 세트 | 장수 | 지금(zero-shot) | linear probe | **전체 학습** | 전체 학습 + 기존 모델(프롬프트 5개만) |
|---|---:|---:|---:|---:|---:|
| OI 상자 | 65 | 78% | 82% | **94%** | 98% |
| OI 봉투 | 6 | 50% | 50% | **83%** | 100% |
| 기존 package_box | 30 | 83% | 93% | **100%** | 100% |
| 기존 package_bag | 25 | 80% | 68% | **96%** | 100% |
| 오탐: OI 가방·문 | 150 | 37% | 17% | **13%** | 29% |
| 오탐: 기존 empty | 30 | 10% | 13% | **3%** | 3% |

- "지금" 열은 지금 서비스 설정(conf 0.25, 프롬프트 14개)이다. linear probe는 conf 0.25에서 빈 복도 오탐이 30%로 늘어 탈락.
- 학습한 모델은 3종류만 안다. 꽃다발·배달 가방·보냉백·케이크 상자를 지키려면 이 5개 프롬프트로 지금 모델을 함께 돌린다(마지막 열). 가방 오탐은 지금보다 낮고(37→29%) 빈 복도는 3%.
- 한계: 평가 사진도 Open Images라 학습 사진과 촬영 방식이 비슷하다. 초인종 시점(문 앞, 아래로 기울어짐)에서는 다시 재야 한다(2단계: 모형 문 촬영).
- 가중치: `data/weights/yoloe-11s-package-oi.pt`(19MB, git 제외, GitHub Release `package-model-v1`). 서비스 적용: 학습 모델(conf 0.4) + 기존 모델 프롬프트 5개(conf 0.25), 두 모델이 같은 물건을 찾으면 하나로 합침(IoU 0.7). 서비스 경로(`YoloVision.detect`)로 다시 잰 값이 위 마지막 열과 같다(사람 인식 포함 한 장 중앙값 약 50ms).
- 남은 오탐 예: 빈 복도 사진 1장(문이 화면을 꽉 채움)을 학습 모델이 상자로 봄(0.52). 화면 80% 넘는 상자를 버리면 없어지지만 가까이 찍은 봉지 사진을 놓쳐(봉지 100→60%) 넣지 않았다. 실제 초인종 사진으로 다시 판단.
- 속도(RTX 3060 Ti, 사진 307장, 한 장 중앙값, 서비스와 같은 FP16): 지금 18.0ms · 학습 모델만 15.1ms · 함께(학습 + 프롬프트 5개) 32.9ms. 함께 돌리면 사진 한 장당 약 15ms가 늘어난다(통합 시험 2차 전체 p95 151ms 기준 약 10%).
- 다시 만들기: `finetune/prep.py`(데이터 고르기·사진 받기) → `finetune/train.py full 30 DATA_ROOT` → `finetune/compare.py DATA_ROOT best.pt 0.4`. 사용법은 각 파일 맨 위.

### 2026-10-04 · 확률 판정 모델 비교: Laya (Jev 호환, 오픈소스) — 불채택

- 빠르기는 40배 빠르지만 한국어 현관 발화에서는 정확도가 쓸 수 없는 수준이다. 공개 자료에도 다국어 의도 분류(MASSIVE, 영어 외) 정확도가 0.45로 나와 있다.

- Jev(TypeSafe)는 같은 방식의 상용 API다. 가중치가 없어 이 PC에서 돌릴 수 없고, 방문객 발화가 외부 서버로 나가며(Zero-Storage 원칙과 충돌), 한국어 성능 자료가 없어 재지 않았다.
