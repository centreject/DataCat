- [x] **G1** 용건을 기획서 9가지(`DELIVERY`·`PICKUP`·`PERSONAL_VISIT`·`SERVICE_VISIT`·`PUBLIC_EMERGENCY`·`SOLICITATION`·`WRONG_VISIT`·`SAFETY_REVIEW`·`UNKNOWN`)와 배송 세부 유형으로 확장, 이름·설명·키워드·예시를 설정 파일 하나로 — 완료: `app/language/purposes.json` 하나만 고치면 LLM 지시문·예시·키워드 규칙·응답 검증이 함께 바뀜. 응답에 `subtype` 추가(DELIVERY만)

- [ ] **G3** 응답에 상태 표시: 요약 대체(원문 사용), 규칙 대체(LLM 실패), 발화 없음
- [ ] **G4** 비전: 동물 감지(`animal`), 꽃·케이크·선물·전단지 인식, 카메라 가림 감지
- [ ] **G5** 🔄 LLM 속도 개선 (음성 처리 p95 2.4초 → 3초 하한 여유 확보) — 진행 중: 9가지 지시문으로 LLM 한 번에 4.4초가 걸려 Pi 타임아웃 초과 위험. 프롬프트 캐시(앞부분 1,679토큰 한 번만 계산) 적용 → 중앙값 2.8초, 답은 동일(GPU 테스트). Qwen3-1.7B bf16은 1.6초지만 용건 81%·긴급 78%라 불채택. 남은 병목: 4bit 토큰 생성 속도(토큰당 65~95ms, 답 약 30토큰)

## 이 파일 관리 규칙 (Claude용)

- **언제 갱신하나:** 작업을 시작할 때(🔄), 끝낼 때(✅ + 커밋 해시), 막히거나 풀릴 때(⏳), 새 작업이 생길 때. 작업 커밋에 이 파일 변경을 함께 넣는다.
- **맨 위 요약:** "지금 하는 일 / 다음 할 일 / 막힌 것"과 단계별 완료 수를 매번 맞춘다.
- **새 작업 추가:**
  1. 성격에 맞는 단계(0–5)에 새 ID로 넣는다. 접두사: E 환경, T 계획 태스크, R 리뷰, P PR, C 팀 협의, M 사소한 문제, F 후속. 기존 번호 사이에 끼울 때는 앞 번호에 문자를 붙인다(예: T6 다음 → T6a).
  2. **진행 순서 표**에도 넣는다. 위치는 의존 관계로 정한다: 필요한 작업보다 뒤, 그 결과를 쓰는 작업보다 앞. 팀원이 필요 없는 일은 팀원을 기다리는 일보다 앞에 둔다.
  3. 변경 기록에 한 줄 남긴다.
- **ID는 바꾸지 않는다.** 취소한 작업은 지우지 말고 ⏭️와 이유를 적는다.
