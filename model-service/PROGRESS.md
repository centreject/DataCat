## 이 파일 관리 규칙 (Claude용)

- **언제 갱신하나:** 작업을 시작할 때(🔄), 끝낼 때(✅ + 커밋 해시), 막히거나 풀릴 때(⏳), 새 작업이 생길 때. 작업 커밋에 이 파일 변경을 함께 넣는다.
- **맨 위 요약:** "지금 하는 일 / 다음 할 일 / 막힌 것"과 단계별 완료 수를 매번 맞춘다.
- **새 작업 추가:**
  1. 성격에 맞는 단계(0–5)에 새 ID로 넣는다. 접두사: E 환경, T 계획 태스크, R 리뷰, P PR, C 팀 협의, M 사소한 문제, F 후속. 기존 번호 사이에 끼울 때는 앞 번호에 문자를 붙인다(예: T6 다음 → T6a).
  2. **진행 순서 표**에도 넣는다. 위치는 의존 관계로 정한다: 필요한 작업보다 뒤, 그 결과를 쓰는 작업보다 앞. 팀원이 필요 없는 일은 팀원을 기다리는 일보다 앞에 둔다.
  3. 변경 기록에 한 줄 남긴다.
- **ID는 바꾸지 않는다.** 취소한 작업은 지우지 말고 ⏭️와 이유를 적는다.
- **남은 작업은 이 파일 하나에만 적는다.** 정확도는 [`eval/README.md`](eval/README.md), 통합 시험은 [`docs/integration-test.md`](../docs/integration-test.md)에 결과만 적는다. 팀 메시지 초안은 로컬 `.superpowers/team-coordination.md`(git 제외, 할 일 목록 없음). 옛 계획 문서는 삭제(10-05, git 기록에 남음).
- **테스트 주기**(같은 날 결정):
  - 단위 테스트(`pytest`, 약 10초): 커밋마다
  - GPU 테스트(`pytest -m gpu`)와 평가(`eval/*`): 모델·프롬프트·`purposes.json`·요약 규칙을 바꿀 때만
  - Docker 확인(`docker/smoke.py`): `requirements*.txt`·`Dockerfile*`이 바뀔 때와 팀에 넘기기 직전
  - **시험용 문장**(`--cases heldout`): 마일스톤(PR 직전 등)에서만 잰다. 틀린 문장을 보고 프롬프트·규칙을 고치지 않는다(고치면 그 세트는 개발용이 됨)
